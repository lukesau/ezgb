# Investigating the 1.05e instability reports

## The question

Was the instability people saw after updating to kernel 1.05e/FW5 a bug in the update itself,
or a consequence of users updating with slow SD cards / weak console batteries?

## What EZ Flash's own release notes establish (paraphrased from their distribution page)

1.05e/FW5 was distributed explicitly as a release candidate, not a final release. Two distinct
risk windows are documented:

1. **During the update:** a slow/low-quality microSD card plus weak console batteries can brick
   the cartridge. A flashing-process risk, not a kernel bug: the notes require a high-quality,
   high-speed card and fresh or externally-powered batteries for the update.
2. **After the update, ongoing:** consoles with a slower SD card hang at the LOADING or OS INIT
   screen. An acknowledged RC-quality runtime bug, left unfixed in this build; the "slow SD
   card" hypothesis matches this window.

EZ Flash recommended staying on FW4/1.04e unless RTC game support or a specific GBC hardware
revision fix was needed. The changelog's stated RC goals: support CGB units without a CPU
suffix (tied to a "Micro SD Initial Error" on those units), rewrite RTC handling to work with
official RTC games, and faster ("turbo") loading on CGB and later hardware.

Hash-verified: `ezgb.dat` / `Update_FW5_7-31.gb` in `juniorkernel-1.05e-FW5/` match the SHA1s
EZ Flash posted (`ce1d531...`, `80ef33a...`), confirmed with `shasum` against this repo's
copies. The analysis covers the genuine RC build, not a corrupted/tampered copy.

## What the disassembly adds

From the 1.04e to 1.05e diff (see `docs/REGISTERS.md` and `docs/DIFF_1.04e_vs_1.05e.md`), the real
logic changes are isolated to bank 0 and bank 1. Several clean insertions in bank 1 (not
present in 1.04e) contain:

- A write sequence: `ld bc,$4000 / ld a,$11 / ld [bc],a` (a standard MBC-style ROM-bank-select
  write) immediately followed by `ld bc,$a000 / ld a,$aa / ld [bc],a`. `$AA` is the first byte
  of a JEDEC NOR flash unlock/write command, consistent with the changelog's "RTC codes are
  rewritten" goal. It is also the BACKUPSAVE pending stamp in battery-backed PSRAM at page `$11`
  (see [psram-save-map.md](psram-save-map.md), `hardware-board.md`), so which operation this
  write performs is unconfirmed until live-traced.
  (`re/1.05e/disassembly/bank_001.asm` around line 4310-4320, in `PreLaunchFramStamp`.)
- A `TIME:` / `SET` / `AUTO SAVE:` string block in bank 0 (offset `0x11910` in the ROM), a
  SET-menu screen for viewing/setting the clock, confirming there's a user-visible, settable
  time value behind this RTC rewrite.
- The existing `BATTERY` / `DRY!!!` low-battery warning (from 1.04e, offset `0x1911` in the
  ROM) is unrelated to this: it's the console-battery warning already shipped in 1.04e's
  "Added a battery dry notice," not an RTC backup battery indicator.

No CGB-revision hardware registers (`$ff4c`-`$ff77` range) are touched anywhere in either
kernel version. If "CGB without CPU suffix" detection is real, it happens through the cart's
own custom FPGA registers (`$7fxx`, see `docs/REGISTERS.md`), not by reading GBC's own
documented/undocumented CPU registers directly.

## Open questions / not yet confirmed

- How RTC battery backup and any flash/PSRAM time image interact (cart coin cell vs console AAs
  during update; which writes in the 1.05e RTC rewrite touch the clock chip vs PSRAM). Save
  memory itself needs the cart battery (`hardware-board.md`).
- Whether the "turbo loading speed" change (faster SD clock/timing for CGB+ devices) tightens
  timeout/retry assumptions enough to explain hangs specifically on slower cards. The SD
  wait-loop's timeout constant in 1.05e is not yet located for comparison against 1.04e; this is
  the most direct way to confirm or rule out the "runtime hang" mechanism.
- Dynamic tracing in SameBoy is the fastest way to nail down the actual loader path and would
  likely resolve the questions above faster than continued static analysis.
